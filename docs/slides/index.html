The problem

Visitors can't find features. Docs tell, they don't show.
Sales engineers don't scale.

  • Trials are lost because people can't find or understand a feature, not because it's missing
  • Static docs and FAQ bots answer in text; the visitor still has to go hunting for the button
  • A human sales engineer can drive the product live, but there's one of them and thousands of visitors
  • Product-tour tools need hand-authored steps for every feature and go stale with every release
The insight

Turn the product itself into the knowledge base, then let the assistant drive it.

  • A running product already encodes its features: routes, navigation, buttons, forms
  • Crawl it like a user would (click things, see what appears) → structured knowledge, not scraped text
  • Give the chatbot hands: a small set of typed, safe actions it can perform in the host page
  • Result: an assistant that says "Sure — watch the screen" and then does it
What we built

One script tag → learns the product → chats, navigates, demos

  • Register a product URL; the worker crawls it and reports stage progress until READY
  • Tenant-isolated knowledge base: pages → features (route, nav path, selectors) → navigation graph → Q&A → demo flows
  • Embedded chatbot answers grounded questions from that knowledge
  • "Take me to analytics" → in-app navigation, chat stays open
  • "Show me how to create a report" → step-by-step demo that highlights, clicks, and types in the live UI
  • Dashboard to watch indexing and browse features, Q&A, demo flows

Sample app "Lumen" indexes in ~12 s without an LLM key: 7 pages · 9 features · 26 Q&A · 9 demo flows. Zero hand-authored steps.

  2. Watch stages: discovering pages → features → navigation → Q&A → demos → READY
  3. Browse Features (route, nav path, selectors, steps), Knowledge, Demo flows

  2. "Take me to analytics." → SPA navigation, chat intact
  3. "Show me how to create a report." → Reports opens, New Report highlighted, explained, clicked; form fields highlighted and filled; live status panel

This exact flow passes in a real browser (Playwright-driven test): 9 typed steps in the report demo. Demos also resume after a full page load.

How it works

Architecture

Three processes. Backend also serves widget.js and the chat iframe (same origin). No queues, no vector DB: thread pool + SQLite (PostgreSQL-compatible schema) + token-overlap retrieval over structured knowledge.

Discovery

Crawl like a user, then structure what you saw

1 · CrawlPlaywright BFS, same origin, ≤25 pages. Optional login step. Per page: title, headings, text, links, buttons, inputs — each with a stable selector.
→
2 · Click-discoverClick each labelled action button from a fresh load; record revealed form inputs or the page it navigates to. Never clicks delete / logout / pay.
→
3 · ExtractOne page feature per page, one action feature per meaningful interaction; nav paths from sidebar labels; site-wide controls deduplicated.
→
4 · GenerateQ&A per feature, a demo flow per feature (navigate → highlight → click → type → explain), knowledge chunks.
  • Selector fallback: data-testid → #id → [name] → [aria-label] → a[href] → shortest unique nth-of-type path; framework-generated volatile ids are skipped
  • Claude enrichment: feature descriptions, product description, and the whole Q&A set — from the discovered structure only, never invented. Templates are the no-key fallback
Demo execution

A pull loop of typed actions, one step at a time

 chat reply {demo_run}  →  iframe: POST /api/demo/runs/{id}/advance {result}
                        ←  {action, message, step_index, total_steps}
 iframe ──postMessage──▶ host bridge executes action ──postMessage──▶ {ok | error}
 iframe advances with the result … until done, FAILED, or Stop
navigateclickhighlightscroll typewaitexplain
  • Navigation requests are one-step runs on the same code path
  • Graceful failure: selector not found after ~3 s → run marked FAILED, chat says "I couldn't find the New Report button on this screen…"
  • SPA navigation via pushState + popstate; if the router didn't react, fall back to a full load
  • Run saved in localStorage before each navigate; the re-injected widget resumes it after a full reload if it landed on the expected path
  • Status panel with step counter, progress bar and Stop; typing uses the native value setter so React-controlled inputs update
Safety & multi-tenancy

The LLM never emits code. Tenants never see each other.

Safety

  • Claude returns text or schema-validated JSON only; never actions, selectors, or scripts
  • Bridge accepts exactly seven typed actions with CSS selectors; unknown types rejected; cross-origin navigation refused
  • Chat runs in an iframe; bridge ↔ iframe messages are origin-checked both ways
  • Crawler skips destructive controls and ignores its own injected widget

Multi-tenancy

  • Every product-scoped row carries tenant_id + product_id
  • Repository functions take both and filter on both; no unscoped reads of product data
  • Dashboard identifies the tenant via header; the widget is keyed by product_id and the tenant is resolved server-side
  • Tenant isolation covered by tests

"You let an AI drive my app?" — No. A whitelist of DOM operations drives it; the AI only chooses among pre-generated, deterministic flows.

Claude's role

An enrichment layer with a deterministic floor

Claude does

  • Indexing: feature descriptions, product description, the full Q&A set — structured output validated against Pydantic schemas
  • Chat: composes 1-3 sentence answers from retrieved knowledge only; says so honestly when the knowledge doesn't cover it (asked about a Salesforce integration, it declines)

Claude never does

  • Intent → action mapping, selectors, demo steps, or anything executed in the host page
  • Block the demo: without a key, templated knowledge, rule-based intents and best-match answers still run end to end

Model: claude-opus-5, low effort for chat answers. A wrong LLM answer can only be wrong text, never a wrong click.

What's next

From MVP to product

  • Finish selector robustness for framework-generated ids (the remaining DentalPin demos)
  • Semantic retrieval (embeddings) on top of the structured knowledge for fuzzier questions
  • Richer demo flows: multi-page journeys, conditional steps, real submissions in sandboxed accounts
  • Chat analytics for the customer: what visitors ask, where demos fail, which features convert
  • Production hardening: auth, PostgreSQL, hosted widget origin, per-tenant rate limits
